03Where should the math happen?

Your Snowflake test (100k series, 14-day rolling z-score, 2–3 s) proved the compute can stay inside Snowflake. Compare the two worlds:

recommended today

A — Compute inside Snowflake

rolling z-score = SQL window functions (AVG / STDDEV OVER)

  • ~2–3 s per 100k series → ~30 s per million
  • Over the wire: anomaly rows only — a handful per chunk
  • Worker RAM: tiny — batch size stops being a safety issue
  • Concurrency: plain asyncio (your chef only waits)
  • Limitation: only algorithms SQL can express
when you outgrow SQL

B — Pull raw data, compute in pandas

any algorithm: STL, Prophet, sklearn, custom models

  • Over the wire: every raw data point of every series
  • Worker RAM: large — batch sizing becomes a real safety concern
  • Concurrency: process pools to dodge the GIL
  • Slower end-to-end; more moving parts to tune
  • Payoff: unlimited algorithm freedom
what travels between worker and snowflake

Start with A behind a swappable detector interface. B then becomes a module you add later — not a rewrite.

04"If Snowflake does the math, why a Python service at all?"

Fair question. Snowflake could host everything: Snowpark runs Python inside it, Tasks schedule it, built-in ML functions even do anomaly detection. Here is the honest tradeoff analysis.

So what does the Python service actually do today?

Translate work orders into SQL, chunk the series set, own retries and error handling, publish results, and be the future home for algorithms that outgrow SQL. Yes — today it is thin glue. That is fine. Its job is to be the seam: algorithm changes ship without touching Java, and Java changes ship without touching the math.

"Java could just call a Snowflake stored procedure" — why not?

Technically possible. But: (1) orchestration — you already have Java + RabbitMQ; Snowflake Tasks would add a second scheduling world with its own failure modes; (2) cost — warehouses bill per second while spinning, pods on the existing K8s cluster are flat cost; (3) deploys — algorithm changes would ship via SQL migrations and admin permissions instead of normal CI/CD with rollback; (4) ownership — the anomaly logic gets one clear owner instead of living in DB-admin land.

Could a notebook be the service?

Notebooks (including Snowflake Notebooks) are exploration tools: no consumers, no health checks, no deploy or rollback story, no alerting. Prototype the SQL there — productionize in the service.

When would all-in-Snowflake actually be right?

A fixed SQL job on a schedule, no external orchestration, small team — then a Snowflake Task is genuinely the clean answer. You are not in that world: you already have a broker, a Java service, and a K8s cluster.

What about future ML — doesn't Snowflake have that too?

Snowpark ML exists and is decent. But iteration speed, library freedom, and local testing live better in your own service. And with the swappable detector interface it is not either/or: a SnowparkML detector can sit behind the same contract if that ever wins on cost or data locality.

05RabbitMQ in five ideas

Everything you actually need, minus the buzzwords.

structure

Queue = mailbox

with a conveyor belt

  • Messages (JSON bytes) wait in order until someone takes them
  • Java drops letters in; you take them out
safety

Ack = signed receipt

"finished — you may destroy it"

  • Only sent after the result is published
  • No receipt (crash)? Letter goes back on the belt for another worker
fairness

prefetch

"at most 10 letters at a time"

  • A slow worker cannot hoard the mailbox
  • Messages keep flowing to healthy workers
failure

DLQ = failed-orders bin

3 strikes and you are out

  • Messages that keep failing are parked, not retried forever
  • One poison message can never block a worker
routing

Exchange = sorting desk

the post office, not your problem

  • Java publishes to an exchange; a routing key decides the queue
  • You mostly just consume from a queue name
rule of thumb

Keep messages small

brokers hate multi-MB payloads

  • Your results fit fine in messages
  • If they ever grow huge: write to S3, send a pointer
playground — try ack vs nack yourself
queue (▸ = next to process)
dead-letter queue
acked (done): 0 dead-lettered: 0

FAIL = nack: the message goes back for another attempt (watch the try counter). After 3 strikes it is dead-lettered — so a broken message can never block the queue.

06Concurrency — the one-chef kitchen

Why threads never speed up your math, and why SQL pushdown makes it all moot.

the process

One chef

your Python process

  • One set of hands, one brain
  • Everything below is about working around this
waiting · I/O

Many pots — asyncio

five pots simmering at once

  • Great when work = waiting (Snowflake, RabbitMQ)
  • Chef is free while pots simmer
compute · GIL

The one-knife rule

only one hand may hold the knife

  • Threads never speed up chopping (CPU math, pandas)
  • The GIL enforces it, always
CPU parallelism

More chefs — processes

ProcessPoolExecutor

  • Actual extra chefs, separate memory each
  • The only way to parallelize CPU work in one pod
scale-out

More kitchens — replicas

K8s just adds pods

  • Zero code changes
  • RabbitMQ spreads messages across replicas automatically
your situation

SQL pushdown = mostly waiting

the chef barely chops

  • Plain asyncio is enough
  • The one-knife rule never bites you

07The messages — the contract with Java

Small, explicit, and always answered. Sign these off with the Java team before coding.

requests queue · from Java
// today: just this — which is a problem (see below)
{
  "request_id": "req-331"
}
results queue · from Python — always sent
{
  "request_id": "req-331",
  "status": "anomalies_found", // or "no_anomalies"
  "computed_at": "2026-09-20T09:01:22Z",
  "anomalies": [
    {
      "series_id": "temp-line7-hourly",
      "ts": "2026-09-19T14:00:00Z",
      "value": 92.4,
      "rolling_mean": 71.2,
      "rolling_std": 6.1,
      "zscore": 3.48,
      "window": 14
    }
  ]
}
Open question #1: request_id alone does not say WHICH series. Something must resolve it — recommended: a shared request-registry table (Java writes the scope when creating the request; Python reads it). Alternatives: self-describing IDs (fragile) or scope-in-message (Java said no). Settle this with the Java team first.
Always respond: even "no_anomalies" gets a message. Silence is ambiguous — done? crashed? lost? Explicit beats implicit, always. And keep result messages small; if full series must ever be attached, switch to S3 + a pointer message.

Open questions before you code

  1. How does request_id resolve to a series set? (shared registry table — settle with Java)
  2. Sign off the result schema: status values, anomaly fields, does Java really need the full series?
  3. Which warehouse size produced the 2–3 s test? Does it auto-suspend (cold start adds ~10–20 s)?
  4. Chunk size: start at ~10k series per query, tune from dev metrics — do not theorize.
